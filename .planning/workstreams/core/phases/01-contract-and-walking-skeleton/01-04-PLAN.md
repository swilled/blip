<objective>
Phase goal (ROADMAP, Phase 1): Both developers build against one frozen contract, and the whole loop (typed utterance -> server -> extension snapshot -> spoken reply) runs on one machine with no Chrome, no voice UI and no Claude.

This plan builds the loopback-only WebSocket hub with the origin and role guard (PROT-04). It leads with a tracer through real sockets (guarded upgrade -> hello -> welcome -> state for a voice client, and a 403 for an evil Origin), then hardens every edge in the research Test Map (role binding, per-role permissions, hello state machine, malformed frames, replacement races, request/response correlation), then adds the CLI flags, optional static serving and the payload-free logging proof.

Purpose: this is the single place roles and Origins are enforced. The Phase 3 guarantee that the confirm phrase is only ever matched on utterances from the voice socket rests on the role-violation refusal built here. The hub runs in parallel with plan 01-03 (no shared files).

Output: `startServer()` usable by tests (port 0) and by the CLI, an `apps/server/test` suite that attacks the hub over real sockets, and a server that the voice developer can point their UI at.

Roadmap success criteria served: 4 (127.0.0.1 only; ordinary-page Origin rejected; utterance from extension refused) and 5 (voice client receives welcome and state). Locked decisions: D-01, D-02, D-03, D-04, D-06, D-14 (not-implemented), D-16 (welcome.brain and state push), D-21 (flags), D-26.
</objective>

  <action>
Implement every behavior above in the hub, keeping the guard pure.

1. Connection state machine (research Pattern 3): `awaiting-hello` with a timer from `helloTimeoutMs` (default `HELLO_TIMEOUT_MS`), then `bound(role)`. Fatal errors send an `error` frame with `fatal: true` and then close with the matching application code from `CLOSE_CODES` (4001, 4002, 4003). A role claim not permitted by the connection's Origin is `role-origin-mismatch` (D-03, D-26). Binary frames get `error` then close 1003.
2. Two-stage inbound handling after binding: `parseFrame` result `ok: false` becomes a non-fatal `error` whose `replyTo` is the offending id when known and whose message uses only the failure code, path strings and messages from the result, never input values; `ok: true` goes through `canSend(connection role, type)`; a refusal sends `error` code `role-violation` and does NOT call any handler (D-04). A hello after binding gets `already-bound`. Never throw out of the message handler; wrap in try/catch and log with the payload-free logger.
3. Routing: first match a pending request by `replyTo` and expected reply type (resolve it and do not dispatch), then built-in `ping` to `pong` (replyTo the ping id), then `handlers[type]` from options, else `error` code `not-implemented` with replyTo (D-14). A `snapshot.result` or `act.result` with no pending request gets `unexpected-reply`. Handlers receive `{ role, message, hub, session }`.
4. Sending: `hub.send(role, type, payload, opts)` builds a validated frame with `buildFrame`, throws when `canReceive(role, type)` is false, returns false when the role has no live connection. `hub.request(role, type, payload, { expect, timeoutMs })` registers a pending entry keyed by the outgoing frame id, rejects on timeout or on disconnect of that role, and cleans up in every path.
5. Replacement and presence (Pitfall 10): one slot per role. A new bound connection replaces the old one: send the old connection `error` code `replaced` (fatal) then close 4004 and log a line; the old socket's `close` handler clears the slot ONLY if the slot still holds that same connection (identity comparison). Presence changes update `session.extensionConnected` and push a fresh `state` to the voice connection if one is bound; a newly bound voice connection gets welcome then state reflecting the current presence.
6. Options (Pitfall 6): `startServer` accepts `extraVoiceOrigins` (validated with `parseAllowedOrigin`, throws on bad input) and passes `dev`, `extensionId` (default EXTENSION_ID) and `helloTimeoutMs` through; the guard closures read the actual bound port.
7. Write the failing tests named in the behavior list first (real sockets, port 0, short timeouts, no fake timers). The D-26 tests go in `security.test.ts` with test names beginning `D-26:`; the rest in `hub.test.ts`.
