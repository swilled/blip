<objective>
Phase goal (ROADMAP, Phase 2): On a real page in Chrome, Blip reads the form's controls and fills them the way a person would, and only ever reports the value the page actually holds.

This plan proves the phase on a real browser. It leads with the I1 tracer (roadmap criterion 5): a voice-role client sends utterances to the server, which drives the real extension on a real test page and speaks values read back from the DOM. It then runs the verification matrix that maps roadmap criteria 1 to 3 to automated checks with page-side evidence (reports from the test pages, no debugger needed), adds the opt-in idle and outage test for criterion 4, writes the developer README, and ends with the manual Chrome/Edge checklist as a blocking human-verify checkpoint.

Purpose: Phase 2 is only done when the real extension has been seen to read, fill and refuse correctly in a real browser, and the open assumptions from research (A1, A3, A5, A6) are closed by a human.

Output: the e2e matrix, `apps/extension/README.md`, and a completed checklist recorded in the SUMMARY.

Roadmap success criteria served: 1, 2, 3, 4 (idle and outage half), 5 (I1). Locked decisions exercised: D-02, D-03, D-05, D-06, D-07, D-12, D-13, D-17, D-18, D-19, D-20. Amendments exercised: A-01, A-02, A-03, A-04, A-05, A-08.

Note on the voice UI: `apps/voice` does not exist in this worktree yet (the voice workstream owns it). The I1 criterion is therefore proven with a voice-role WebSocket client (the same role and Origin rules the voice UI uses, which ROADMAP explicitly allows as "fake acceptable"); checklist row M17 repeats it with the voice developer's real UI if it has landed by then.
</objective>
